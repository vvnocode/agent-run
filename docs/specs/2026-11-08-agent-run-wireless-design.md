# Agent Run! 无线连接设计方案（v1.1：蓝牙）

- 日期：2026-11-08
- 状态：2026-11-08 已确认并实现，W2、W3、W5、W6 待实测（见 §7.2）
- 前置：[v1 设计方案](2026-11-08-agent-run-design.md)（USB 版，已实现）
- 目录说明：文中的 `bridge/` 现为 `transports/macos-ble/`，固件在 `displays/ai-passport/`

## 1. 目标

1. 不插数据线时，设备放在 Mac 附近（同一房间）照常显示会话数、跑速和“等你处理”。
2. 插着 USB 时行为与 v1 完全一致；拔线后自动切到蓝牙，插回后自动切回 USB。
3. 电池供电时降低功耗，并给出实测续航。

## 2. 非目标

- 离开 Mac 蓝牙范围后仍能显示（需要 Wi-Fi 加服务器中转，另写 spec）。
- 一台设备同时连多台 Mac，或一台 Mac 同时连多台设备。v1.1 只做一台对一台。
- 经 iPhone 中转。
- 蓝牙下的固件升级（仍用 USB 烧录）。

## 3. 方案选择

| 方案 | 能用的范围 | 设备端 | 电脑端 | 结论 |
|---|---|---|---|---|
| **A. 蓝牙直连（采用）** | Mac 附近，通常同一房间，实际距离要实测 | 广播一个 GATT 服务，沿用 v1 的行协议 | 新增一个带蓝牙权限的桥接小程序 | 不用配网，耗电最低；状态牌本来就跟着 Mac 走 |
| B. Wi-Fi 局域网 | 同一 Wi-Fi 下的整个家里或办公室 | 要配网（官方小程序 BLUFI），Wi-Fi 常连 | 守护进程监听端口，用 mDNS 让设备找到 Mac | 要处理配网、换网络、macOS 防火墙弹窗和局域网鉴权；Wi-Fi 常连更耗电。只有需要跨房间时才值得做 |
| C. Wi-Fi + 云端中转 | 任何有网的地方 | 同 B | 守护进程把状态推到自建服务器 | 要运维服务器，状态数据出本机。等做好友联机时再一起做 |

蓝牙方案内部又有两个取舍：

| 问题 | 采用 | 被否 |
|---|---|---|
| 电脑端谁来连蓝牙 | Swift 写的桥接小程序（CoreBluetooth），作为登录项后台运行 | Python 标准库没有蓝牙。第三方库 bleak 依赖 pyobjc，而且 macOS 的蓝牙权限归属于带 Info.plist 的应用，由 launchd 启动的 `python3` 很可能拿不到权限（S0 实测确认） |
| 谁当主动方 | 设备做外设（peripheral）并广播，Mac 主动连接 | 设备当中心去连 Mac：macOS 不方便作为可连接的外设长期广播 |

## 4. 设备端

### 4.1 蓝牙服务

- 使用 NimBLE 外设角色，广播名 `AgentRun-XXXX`（MAC 地址后两字节）。
- GATT 服务沿用 Nordic UART 的 UUID 布局（`6e400001/2/3-b5a3-f393-e0a9-e50e24dcca9e`），与社区四子棋相同，通用 BLE 调试工具可以直接连。
  - RX 特征：主机写入（无响应写），内容是 v1 协议的字节流；
  - TX 特征：设备通知，用来回复 `AR1 HELLO`。
- 协议本身不变。v1 的行装配器 `ar_line_push()` 已能处理任意分片，所以超过一次写入长度的帧由主机分片写入即可。
- 每个特征都要有 `access_cb`，描述符发现收到 `EDONE` 不等于失败。这两个坑见社区文档 `two-device-ble-link`。

### 4.2 配对与绑定

实施决定（2026-11-08）：直接采用下文的退路方案，即 LE Secure Connections 的 Just Works 配对加设备上按 OK 确认，设备声明无输入输出能力。这样不依赖 macOS 是否支持数字比较弹窗。原方案保留如下，作为被否方案：

- 使用 LE Secure Connections 绑定，设备端 IO 能力为“有显示、能确认”。
- 第一次有 Mac 连接时，屏幕显示“配对这台 Mac？按 OK 确认，按下取消”。确认后，绑定信息写入 NVS（`CONFIG_BT_NIMBLE_NVS_PERSIST=y`）。
- 已有绑定时只接受已绑定的主机；其他设备连上来不处理数据，30 秒后断开。
- 长按上键 5 秒清除绑定，用于换电脑。
- macOS 在这种配对下是否弹出系统确认框、弹什么，S0 阶段实测。如果走不通，退回“Just Works 配对 + 设备上按 OK 确认”。

### 4.3 两条链路并存

- USB 与蓝牙同时开启。设备取两条链路中最近到达的合法帧显示。主机同一时刻只用一条链路发送，所以不会出现两路内容冲突。
- 标题栏图标按最近一帧的来源显示：USB 插头或蓝牙标志。

### 4.4 省电（只在没接 USB 主机时生效）

USB 主机是否在线用 `usb_serial_jtag_is_connected()` 判断（ESP-IDF 5.5.3 提供）。

| 项目 | 规则 |
|---|---|
| 背光 | 状态 30 秒没有变化，降到最低档（20%）；进入“等你处理”或按任意键，恢复设定亮度；“未连接”5 分钟后关闭，与 v1 相同 |
| 动画 | 背光在最低档时，帧间隔放慢为正常值的 2 倍 |
| 连接参数 | 设备请求 500 ms 左右的连接间隔（实际由 Mac 决定，要实测） |
| 心跳与超时 | 走蓝牙时主机心跳 5 秒、设备超时 15 秒（USB 仍为 2 秒和 10 秒） |
| 深度睡眠 | 不进入（会断开蓝牙） |

### 4.5 资源预算

- 社区实测 NimBLE 链路约占 60 KB 堆；v1 开机后空闲 131 KB、最大连续块 112 KB，预计开蓝牙后还剩约 70 KB，以实测为准。
- `sdkconfig.defaults` 重新打开蓝牙，只开外设与广播两个角色，最多 1 个连接。

## 5. 电脑端

### 5.1 桥接小程序 `AgentRunBridge.app`

- Swift 编写，用 CoreBluetooth。作为登录项在后台运行（不显示 Dock 图标），Info.plist 声明蓝牙用途说明。首次运行时由 macOS 弹出蓝牙权限请求，用户允许后才能使用。
- 本机自用，ad-hoc 签名即可，不做公证。
- 职责：扫描并连接已绑定的设备、分片写入、读取 HELLO、断线后自动重连；不解析会话状态。

### 5.2 与守护进程的分工

- 守护进程仍负责全部状态汇总。它把链路抽象成“USB 链路”和“蓝牙链路”两种：USB 端口在时用 USB，否则把状态行写到桥接小程序的本机 socket（`~/.agent-run/run/ble.sock`）。
- 桥接小程序通过同一个 socket 回报连接状态，`agent-run status` 显示“蓝牙已连接 AgentRun-XXXX”。
- 新增命令 `agent-run pair`：让桥接小程序扫描附近的 `AgentRun-*` 设备并发起配对。

## 6. 测试与验收

### 6.1 宿主测试（先写测试）

- **设备端纯 C 模块：** 省电规则（30 秒降亮度、等你处理恢复、按键恢复）；绑定状态机（无绑定、待确认、已绑定、清除）；两条链路取最近一帧。
- **守护进程：** 用假链路测试 USB 优先、拔线后改走蓝牙、插回后切回 USB、蓝牙下的心跳间隔。
- **桥接小程序：** 分片写入与重连逻辑的单元测试（Swift XCTest）。

### 6.2 验收标准

| 编号 | 标准 |
|---|---|
| W1 | 拔掉数据线后 15 秒内改走蓝牙，计数与“等你处理”正常；状态变化到屏幕更新不超过 3 秒 |
| W2 | Mac 睡眠唤醒、关开蓝牙、设备走出范围再回来，这三种情况下 30 秒内自动重连 |
| W3 | 未绑定的另一台电脑或手机连上设备，屏幕不显示它发来的数据 |
| W4 | 插回 USB 后 5 秒内回到 USB，显示不中断 |
| W5 | 电池供电连续运行 2 小时，记录电量变化并推算续航，写回本文件；不预设目标值 |
| W6 | 开蓝牙后的最小空闲堆、最大连续块记录在案，连续运行 8 小时不重启 |
| W7 | v1 的全部验收项不退化 |

## 7. 里程碑

1. **S0 可行性验证（一次性探路，代码不保留）：**
   - 一个最小 Swift 程序作为登录项运行，确认能拿到蓝牙权限并连上设备；
   - 确认 macOS 在 LE Secure Connections 绑定时的系统提示；
   - 在现有界面上开启 NimBLE，记录内存。
2. **B1 设备端：** 实现 §4，以及 §6.1 的设备端测试。
3. **B2 电脑端：** 实现桥接小程序与守护进程的链路切换。
4. **B3 联调：** 完成 W1–W7，把续航数据写回本文件。

### 7.1 S0 结果（2026-11-08）

| 项目 | 结果 |
|---|---|
| 蓝牙权限 | 打包成 .app（Info.plist 带蓝牙用途说明、ad-hoc 签名）后用 `open` 启动，macOS 弹出权限请求，用户允许后 `CBManager.authorization` 为允许 |
| 配对 | Just Works 配对完成；设备显示“配对这台电脑？”，用户按 OK 后才开始采纳数据。Mac 端没有出现需要额外处理的配对窗口 |
| 通信 | 发现、连接、订阅通知、写入状态帧、收到 HELLO 通知都正常；MTU 协商为 256，单次写入上限 512 字节 |
| 设备内存 | 默认蓝牙配置下开机空闲堆只剩 32 KB；按 `sdkconfig.defaults` 裁剪（关扫描、BLE 5.0、测试模式，缩小缓冲）后为 57 KB，最大连续块 48 KB |
| 未覆盖 | 由 launchd 在后台启动时的权限归属；重新签名（每次重编译 cdhash 都会变）后是否要重新授权 |

据此：§4.2 采用 Just Works 加设备确认；不再单独做 `agent-run pair` 命令，桥接程序自动连接附近的 `AgentRun-*` 设备，是否接受由设备上的确认决定。

### 7.2 B1–B3 实施记录（2026-11-08）

- **已实现：**
  - 设备端蓝牙服务、配对确认、长按上键 5 秒清除配对、电池供电时降背光、按来源区分链路超时；
  - 桥接程序 `bridge/`（Swift，`BridgeCore` 有单元测试）及其 LaunchAgent `local.agent-run.bridge`；
  - 守护进程的 USB 优先与蓝牙回退。
- **实测通过：**
  - 由 launchd 直接运行 .app 内的可执行文件时，用户允许后能拿到蓝牙权限；
  - 桥接程序与 S0 探路程序属于同一台 Mac，沿用已有绑定，不用再次确认；
  - 拔掉 USB 后 0.3 秒改走蓝牙（W1）；插回后在下一次检查时切回 USB（W4）。
- **尚未验证：** W2（睡眠唤醒、关开蓝牙、走出范围）、W3（其他电脑被拒绝）、W5（续航）、W6（连接状态下的内存与 8 小时运行）。
- **已知现象：** 用 esptool 烧录后，设备有时不响应握手，复位一次即恢复，原因未查明。

## 8. 风险与待核实

| 事项 | 影响 | 处理 |
|---|---|---|
| macOS 后台应用的蓝牙权限与配对提示 | 桥接小程序连不上或用户看不到确认 | S0 先验证；不行就改成需要手动打开一次的菜单栏应用 |
| 实际通信距离（板载天线、透明外壳、佩戴在身上） | 走开几步就断 | B3 实测并写回；断开时显示“未连接”，靠近后自动恢复 |
| 续航未知，背光大概率是主要耗电 | 一天用不完 | W5 实测后再调整 §4.4 的规则 |
| 蓝牙与 USB 并存的内存 | 低内存时崩溃 | W6 记录；必要时 USB 在线时不启动蓝牙广播 |
