# Agent Run! 无线连接设计方案（v1.1：蓝牙）

- 日期：2026-11-08
- 状态：2026-11-08 已确认并实现，W2、W3、W5、W6 待实测（见 §7.2）
- 前置：[v1 设计方案](2026-11-08-agent-run-design.md)（USB 版，已实现）
- 目录说明：文中的 `bridge/` 现为 `transports/macos-ble/`，固件在 `displays/ai-passport/`

## 1. 目标

1. 不插数据线时，设备放在 Mac 附近（同一房间）照常显示会话数、跑速和“等你处理”。
2. 插着 USB 时行为与 v1 完全一致；拔线后自动切到蓝牙，插回后自动切回 USB。
3. 电池供电时降低功耗，并给出实测续航。

## 2. 非目标

- 离开 Mac 蓝牙范围后仍能显示（需要 Wi-Fi 加服务器中转，另写 spec）。
- 一台设备同时连多台 Mac，或一台 Mac 同时连多台设备。v1.1 只做一台对一台。
- 经 iPhone 中转。
- 蓝牙下的固件升级（仍用 USB 烧录）。

## 3. 方案选择

| 方案 | 能用的范围 | 设备端 | 电脑端 | 结论 |
|---|---|---|---|---|
| **A. 蓝牙直连（采用）** | Mac 附近，通常同一房间，实际距离要实测 | 广播一个 GATT 服务，沿用 v1 的行协议 | 新增一个带蓝牙权限的桥接小程序 | 不用配网，耗电最低；状态牌本来就跟着 Mac 走 |
| B. Wi-Fi 局域网 | 同一 Wi-Fi 下的整个家里或办公室 | 要配网（官方小程序 BLUFI），Wi-Fi 常连 | 守护进程监听端口，用 mDNS 让设备找到 Mac | 要处理配网、换网络、macOS 防火墙弹窗和局域网鉴权；Wi-Fi 常连更耗电。只有需要跨房间时才值得做 |
| C. Wi-Fi + 云端中转 | 任何有网的地方 | 同 B | 守护进程把状态推到自建服务器 | 要运维服务器，状态数据出本机。等做好友联机时再一起做 |

蓝牙方案内部又有两个取舍：

| 问题 | 采用 | 被否 |
|---|---|---|
| 电脑端谁来连蓝牙 | Swift 写的桥接小程序（CoreBluetooth），作为登录项后台运行 | Python 标准库没有蓝牙。第三方库 bleak 依赖 pyobjc，而且 macOS 的蓝牙权限归属于带 Info.plist 的应用，由 launchd 启动的 `python3` 很可能拿不到权限（S0 实测确认） |
| 谁当主动方 | 设备做外设（peripheral）并广播，Mac 主动连接 | 设备当中心去连 Mac：macOS 不方便作为可连接的外设长期广播 |

## 4. 设备端

### 4.1 蓝牙服务

- 使用 NimBLE 外设角色，广播名 `AgentRun-XXXX`（MAC 地址后两字节）。
- GATT 服务沿用 Nordic UART 的 UUID 布局（`6e400001/2/3-b5a3-f393-e0a9-e50e24dcca9e`），与社区四子棋相同，通用 BLE 调试工具可以直接连。
  - RX 特征：主机写入（无响应写），内容是 v1 协议的字节流；
  - TX 特征：设备通知，用来回复 `AR1 HELLO`。
- 协议本身不变。v1 的行装配器 `ar_line_push()` 已能处理任意分片，所以超过一次写入长度的帧由主机分片写入即可。
- 每个特征都要有 `access_cb`，描述符发现收到 `EDONE` 不等于失败。这两个坑见社区文档 `two-device-ble-link`。

### 4.2 配对与绑定

实施决定（2026-11-08）：直接采用下文的退路方案，即 LE Secure Connections 的 Just Works 配对加设备上按 OK 确认，设备声明无输入输出能力。这样不依赖 macOS 是否支持数字比较弹窗。原方案保留如下，作为被否方案：

- 使用 LE Secure Connections 绑定，设备端 IO 能力为“有显示、能确认”。
- 第一次有 Mac 连接时，屏幕显示“配对这台 Mac？按 OK 确认，按下取消”。确认后，绑定信息写入 NVS（`CONFIG_BT_NIMBLE_NVS_PERSIST=y`）。
- 已有绑定时只接受已绑定的主机；其他设备连上来不处理数据，30 秒后断开。
- 长按上键 5 秒清除绑定，用于换电脑。
- macOS 在这种配对下是否弹出系统确认框、弹什么，S0 阶段实测。如果走不通，退回“Just Works 配对 + 设备上按 OK 确认”。

### 4.3 两条链路并存

- USB 与蓝牙同时开启。设备取两条链路中最近到达的合法帧显示。主机同一时刻只用一条链路发送，所以不会出现两路内容冲突。
- 标题栏图标按最近一帧的来源显示：USB 插头或蓝牙标志。

### 4.4 省电与亮屏

USB 主机是否在线用 `usb_serial_jtag_is_connected()` 判断（ESP-IDF 5.5.3 提供）。它看的是能否持续收到主机发来的 SOF 帧，跟有没有供电无关：接充电宝，或者 Mac 睡眠导致 USB 挂起时，它都返回 false。板上也没有检测 USB 供电或充电状态的引脚，所以固件分不清“电池供电”和“插着 USB 但主机在睡眠”。

| 项目 | 规则 |
|---|---|
| 亮屏事件 | 按键、等你处理的数量增加、有会话完成、连上电脑、出现配对确认、开机，以及拔掉 USB 时屏幕亮着。背光按最近一次亮屏事件计时。按键以按下为准，熄屏时按下的这次手势只亮屏、不执行操作。2026-11-08 修订，理由见 §7.4；2026-11-09 修订，理由见 §7.5 |
| 背光（电池供电） | 亮屏期间用低亮度（20%，设定亮度更低时用设定值），30 秒后熄屏 |
| 背光（插着 USB 主机） | 5 分钟内用设定亮度，之后降到低亮度，30 分钟后熄屏，以保护屏幕与背光；“未连接”且 5 分钟内无亮屏事件时熄屏，与 v1 相同 |
| 背光（配对确认） | 始终用设定亮度 |
| 动画 | 背光低于设定亮度时，帧间隔放慢为正常值的 2 倍；熄屏时停止 |
| 连接参数 | 设备请求 500 ms 左右的连接间隔（实际由 Mac 决定，要实测） |
| 心跳与超时 | 走蓝牙时主机心跳 5 秒、设备超时 15 秒（USB 仍为 2 秒和 10 秒） |
| 深度睡眠 | 前提是没接 USB 主机、电量计读得到电量、不在配对确认中、入睡时按键是松开的，再满足以下任一条件即进入：“未连接”且无按键都已满 30 分钟；屏幕持续熄灭满 1 小时（在线时也适用）。只能按任意键唤醒，唤醒后重新启动并自动重连。2026-11-08 修订，原规则为“不进入”，理由见 §7.3；2026-11-09 增加熄屏 1 小时的条件，理由见 §7.5 |

### 4.5 资源预算

- 社区实测 NimBLE 链路约占 60 KB 堆；v1 开机后空闲 131 KB、最大连续块 112 KB，预计开蓝牙后还剩约 70 KB，以实测为准。
- `sdkconfig.defaults` 重新打开蓝牙，只开外设与广播两个角色，最多 1 个连接。

## 5. 电脑端

### 5.1 桥接小程序 `AgentRunBridge.app`

- Swift 编写，用 CoreBluetooth。作为登录项在后台运行（不显示 Dock 图标），Info.plist 声明蓝牙用途说明。首次运行时由 macOS 弹出蓝牙权限请求，用户允许后才能使用。
- 本机自用，ad-hoc 签名即可，不做公证。
- 职责：扫描并连接已绑定的设备、分片写入、读取 HELLO、断线后自动重连；不解析会话状态。

### 5.2 与守护进程的分工

- 守护进程仍负责全部状态汇总。它把链路抽象成“USB 链路”和“蓝牙链路”两种：USB 端口在时用 USB，否则把状态行写到桥接小程序的本机 socket（`~/.agent-run/run/ble.sock`）。
- 桥接小程序通过同一个 socket 回报连接状态，`agent-run status` 显示“蓝牙已连接 AgentRun-XXXX”。
- 新增命令 `agent-run pair`：让桥接小程序扫描附近的 `AgentRun-*` 设备并发起配对。

### 7.3 电池供电时的深度睡眠（2026-11-08）

- **问题：** 原规则下，“未连接”5 分钟后只关背光，CPU、蓝牙广播和主循环照常运行，也没有开启电源管理。典型场景是下班合上 Mac、设备留在桌上，此后整夜什么都不显示，却持续耗电。按 ESP32-C3 不开 light sleep 时的典型电流估算，500 mAh 电池约 12–25 小时就会耗尽（估算值，W5 未实测）。
- **决定：** 按 §4.4 的条件进入深睡，按键唤醒。各外设入睡前的准备沿用上游 BSP 提供的接口；按 ESP-IDF 要求，入睡前先停止 NimBLE。唯一的例外是电量计：入睡前不调用 `bsp_battery_sleep()`，让 CW2017 保持工作。实测 CW2017 休眠后再激活时会重新开始估算，醒来后电压约 200 ms 内就有读数，但电量要约 10 秒后才正确，在此之前读到 0%，界面会显示 0% 电量。保持工作只多耗电量计自身的电流。
- **“电量计读得到电量”这一条：** 用来避免误伤没装电池、只靠 Mac 的 USB 供电的设备。没有这一条的话，Mac 睡眠时这类设备会深睡，Mac 醒来后不会自己恢复显示。这一条的前提是“没装电池时 CW2017 读不到数据”，尚未在真机上确认。如果读得到，这类设备在 Mac 睡眠超过 30 分钟后也会深睡，需要按键唤醒。
- **已知代价：** 装着电池并插着 USB 时，如果 Mac 睡眠超过 30 分钟，设备也会深睡，Mac 醒来后要按一下键（原因见 §4.4 对 USB 主机检测的说明）。
- **被否方案：**
  - 维持不深睡：深睡后需要按键才能恢复，但长时间离开 Mac 时持续耗电的代价更大；
  - 定时唤醒、短暂广播后再睡：Mac 回来后能自动恢复，但每次唤醒都要重启并初始化屏幕和蓝牙，实现和验证成本高。等 W5 数据显示有必要时再考虑；
  - 开启电源管理和自动 light sleep、保持蓝牙连接：要改掉 20 ms 主循环和 LVGL 刷新节奏，并确认板上 32 kHz 时钟源，改动面大，留到 W5 之后评估。
- **上板验证（2026-11-08）：** 用临时测试固件验证，改动不入库：时限缩为 60 秒，忽略“没接 USB 主机”这一条，增加电量与唤醒原因日志。共做了三轮入睡和唤醒，以串口日志和端口的消失、重现为准：
  - 入睡流程按顺序完成：停蓝牙、ES8311 休眠并校验寄存器、I2S 引脚高阻、ST7789 休眠、确认按键已松开；入睡后串口断开，20 秒以上没有自行醒来；
  - 按任意键唤醒，唤醒原因为 `ESP_SLEEP_WAKEUP_GPIO`（`0x80`）；
  - 保持电量计工作后，醒来第一次读数就是正确电量（97%）。
- **仍待验证：**
  - 深睡电流；
  - 真实条件下的触发：电池供电、没有 USB 主机、等满 30 分钟；
  - 按键唤醒后的蓝牙自动重连（定时唤醒已验证，见下一条）；
  - 没装电池时电量计是否读不到。
- **测试中发现的配对丢失（2026-11-08 查明并修复）：**
  - 根因：ESP-IDF 5.5 的 NimBLE 要等读完对端版本，才上报 `BLE_GAP_EVENT_CONNECT`。设备重启后，已绑定的 Mac 立刻重连并先完成加密，`ENC_CHANGE` 比 `CONNECT` 先到。旧代码用 `CONNECT` 时记下的绑定数判断是否为新配对；开机后的第一条连接里这个数还是初值 0，于是把这次重连当成新配对。设备已有绑定，按规则拒绝，并删除了 Mac 的绑定。是否丢失取决于两个事件谁先到，所以复位、重烧和深睡唤醒都会偶发。
  - 订正：原先记录为“Mac 发起重新配对，固件按 `BLE_GAP_EVENT_REPEAT_PAIRING` 删除绑定”，这个判断有误。NVS 里被删的条目与 `ble_store_util_delete_peer()` 的删除范围一致，删除后没有写 `paired`；`paired` 置 0 是下一次开机发现“没有绑定却有标记”后补写的。诊断固件的日志也显示，删除来自 `on_enc_change()` 里的拒绝。
  - 修复：判断新配对的基线改为“已确认的绑定数”（`ar_pair_encrypted()`），在开机、确认和清除时更新，不再依赖连接建立事件。连接建立和加密两个事件都登记当前连接，后到的 `CONNECT` 不再清掉加密时建立的信任。
  - 验证：重新配对后，复位 1 次，`idf.py flash` 4 次（其中 2 次出现加密先于连接建立），深睡 3 次（临时测试固件强制入睡，15 秒后定时唤醒，改动不入库）。每次绑定都保留，Mac 自动重连并收到 HELLO。

### 7.4 通知、亮屏、电量、音量与设置菜单（2026-11-08）

参考社区玩法“Codex 桌面伙伴”（玩法 270）的完成提示与息屏规则，按用户要求增加以下功能：

- **完成提示：** 设备比较相邻两帧的 `done`（今日完成轮数），变大即有会话完成。状态行显示约 5 秒“完成 +N”，状态行与底栏“今日完成”变为强调色，并播放一声比“等你处理”轻的三音上行提示。
  - 不算完成的情况：刚连上或掉线恢复后的第一帧只作基准，离线期间累计的完成不提示；跨天清零时 `done` 变小，只更新基准。
  - 同一帧里等你处理也增加时，只响“等你处理”。完成提示音与上一次任意提示音至少间隔 10 秒，其间的完成合并、不补响。
  - 用的是协议里已有的字段，采集端与协议都不用改。
- **通知亮屏与息屏：** 规则见 §4.4。插着 USB 主机时 5 分钟降低亮度、30 分钟熄屏，是用户在评审时提出的，用于保护屏幕。
- **电量显示：** 标题栏电池图标左侧用 1 倍像素字显示百分比，读不到时不显示，低于 20% 用橙色。v1 设计曾因 2 倍像素字放不下而不显示百分比。
- **音量：** 分 静音、低、中、高 四档，替代原来的静音开关。中档等于改版前的固定音量（ES8311 输出 60%），保存到 NVS（键 `vol`）。没有 `vol` 时沿用旧的 `mute` 键，静音读作 0 档。标题栏用喇叭加 1–3 根档位条表示音量，静音时为喇叭加叉号。
- **设置菜单：** 音量和亮度都从设置菜单调节，状态切换见 `ar_menu_key()` 与 `ar_menu_tick()`。
  - 首页单击确定键打开一级菜单，列出“音量”“亮度”两行，默认选中音量。首页的上下键暂不分配功能，留给以后切换显示各工具的 5 小时与 7 天用量。
  - 一级菜单里上下键切换选中项，到头停住；单击确定进入二级；双击确定回首页；10 秒没有按键回首页。
  - 二级里上下键加减一档，到头停住，立即保存。调音量时每按一次按新音量试听一声，静音不响；调亮度时按设定亮度点亮，电池供电时也一样，让用户看到实际效果。双击确定回一级并保留选中项，单击确定不起作用；3 秒没有按键直接回首页。
  - 上下键快速连按两下会被按键组件识别成双击，按两步处理，免得调节时丢档。长按不分配功能。
  - 熄屏时第一下按键只点亮屏幕。出现配对确认时关闭菜单，按键交给配对确认。
- **菜单界面：** 面板盖住标题栏以下的区域，标题栏的电量与音量图标保持可见；菜单打开时其余画面元素隐藏，被盖住的动画不再重绘。面板沿用现有卡片的深色底、圆角和细边框。
  - 一级每行依次是像素图标、名称、小档位条、当前值和 `›`。选中行加深底色、加黄色描边，图标、档位条和当前值用强调色；未选中行用暗色。底部提示“确定进入 · 双击返回”。
  - 二级标题前有 `‹`，右上角是当前值；中间是放大的像素图标（喇叭加三道声波，或像素太阳）；下方是由矮到高的档位条（音量 3 根、亮度 5 根），右侧有 ▲▼；底部提示“上下调节 · 双击返回”。静音时喇叭变灰并画橙色叉号，当前值用橙色。
  - “等你处理”画面底部右侧的提示改为“确定键设置”。
- **主任务栈改为 7168 字节：** 串口截屏在主任务里调用 `lv_refr_now()` 渲染整屏。第一版音量浮层加上后对象嵌套变深，截屏时 4096 字节的栈溢出（`Stack protection fault`）。实测峰值约 4.5 KB，改为与 LVGL 任务相同的 7168 字节后剩余约 2.6 KB。设置菜单的元素直接放在分组里，不再套一层行容器，嵌套深度与浮层相同；连续截屏 20 次后剩余约 2.5 KB。以后在界面上加元素，要用截屏复核这个余量。
- **被否方案：**
  - 拿起设备亮屏：官方硬件规格与 BSP 都没有加速度计或其他运动传感器。用麦克风听敲击声，需要音频芯片一直工作，待机耗电明显上升，还容易误触发；
  - 长按确定键循环切换音量：第一版就是这样做的，用户试用后要求改为上下键直接加减，并显示当前音量；
  - 首页上下键直接调音量、长按确定键循环切换亮度，并显示 1 秒自动消失的浮层：第二版就是这样做的，用户随后改为统一从设置菜单调节，首页上下键留作他用；
  - 用电源键返回上一级：电源键直接控制硬件电源（按住 0.5 秒开机、约 2 秒关机），不在官方引脚表里，ESP32-C3 也没有空闲引脚接它，固件收不到它的按键事件。改用双击确定键返回；
  - 长按确定键返回，或在一级菜单加一行“返回”：用户选了双击确定；
  - 息屏时长做成可调设置：用户这一轮只要音量和亮度两项；
  - 电池供电时，“等你处理”期间保持亮屏：用户可能长时间不在设备旁，优先省电。每个新的等你处理都会重新亮屏，有未处理项时按键即可查看；
  - 由采集端新增“完成”事件：`done` 已能表达完成，而且设备端可以去重和处理掉线恢复，不必改协议。

### 7.5 熄屏关机、按键亮屏与拔线熄屏（2026-11-09）

- **熄屏 1 小时关机：** 按用户要求，电池供电时屏幕持续熄灭满 1 小时即进入深睡，在线时也适用。电源键直接控制硬件电源，固件无法切断电源（见 §7.4），所以“关机”就是 §4.4 的深度睡眠，按任意键唤醒。
  - 等你处理增加、有会话完成都会点亮屏幕并重新计时，所以只有 1 小时以上没有任何通知和按键才会关机。代价是关机后新的“等你处理”不再提醒，要按键唤醒。
  - 插着 USB 主机时不关机：此时电池在充电，没有省电的必要；关机还会让设备从电脑上消失，不再提醒。
- **按任意键亮屏：** 原实现只在按键组件发出单击、双击、长按事件时亮屏。按键组件（espressif/button 4.2.0）对以下手势不发这三种事件，熄屏时按下后屏幕不亮：
  - 三连击及以上（组件只在连击 1 次、2 次时发单击、双击）；
  - 双击的第二下按住超过 180 ms 又不足 500 ms（组件直接结束本次手势）。

  现在改为任意键按下即亮屏。熄屏时按下的这次手势，其后的单击、双击或长按都不执行，规则见 `ar_keywake_*()`：每次手势最多产生一个动作，吞掉一个即结束；手势没有产生动作就结束时（如三连击），下一次按下与上次松手相隔不少于 250 ms 即视为新手势，不再吞掉。按住上键 5 秒清除配对照常生效。
- **拔掉 USB 后熄屏：** 插着 USB 主机时按“亮屏事件后 30 分钟熄屏”计时，电池供电时按“30 秒”计时。拔线瞬间改用电池规则，如果最近一次亮屏事件已在 30 秒以前，亮着的屏幕会立刻熄灭。用户遇到的场景是：插着 USB 熄屏，有会话完成后亮屏，过一会儿拔掉 USB，屏幕随即熄灭。现在拔线时屏幕若亮着，就补记一次亮屏事件，按电池规则继续低亮度亮 30 秒，见 `ar_power_update()`。
  - 屏幕已熄灭时拔线不点亮。Mac 睡眠导致 USB 主机离线时，固件同样看到“拔线”（见 §4.4），这样不会在 Mac 睡眠时点亮屏幕。
  - 插上 USB 不另算亮屏事件：从未连接变为连上电脑本来就会亮屏。
- **被否方案：**
  - 插着 USB 主机时也在熄屏 1 小时后关机：没有省电收益，反而错过后续提醒；
  - 关机时间做成设置项：用户只要求 1 小时；
  - 拔线时一律点亮屏幕：Mac 睡眠时会无故亮屏 30 秒。

## 8. 风险与待核实

| 事项 | 影响 | 处理 |
|---|---|---|
| macOS 后台应用的蓝牙权限与配对提示 | 桥接小程序连不上或用户看不到确认 | S0 先验证；不行就改成需要手动打开一次的菜单栏应用 |
| 实际通信距离（板载天线、透明外壳、佩戴在身上） | 走开几步就断 | B3 实测并写回；断开时显示“未连接”，靠近后自动恢复 |
| 续航未知，背光大概率是主要耗电 | 一天用不完 | W5 实测后再调整 §4.4 的规则 |
| 蓝牙与 USB 并存的内存 | 低内存时崩溃 | W6 记录；必要时 USB 在线时不启动蓝牙广播 |
